# False positive analysis

## Source run and definitions

- Source run: `python tools/evaluate.py --rescore` of the reports in `data/eval-tmp/` at commit 2ae19e3 (static layers only): 53 benchmarks, 52 true positives, 18 false positives, precision 0.74, recall 0.98.
- False positive (A1-1 definition in `tools/evaluate.py`): some Secure finding has a CWE that is exactly one of the benchmark's `cwe_ids`, is on the benchmark's `vulnerable_component`, and does not have confidence low.
- Each Secure APK (and its Benign APK, for comparison) was decoded again with apktool and its smali and manifest read; the Java sources under `benchmarks/ghera/<category>/<folder>/{Benign,Secure}/app/src/main` were diffed to see what the Secure fix changed. Every one of these APKs has `targetSdkVersion` 27 and `minSdkVersion` 27.
- "Finding still true on Secure" means the Secure APK really has the property the rule reports; the benchmark's fix is somewhere else. Such a finding counts as a false positive only because the benchmark lists the CWE for that component.

## Summary by cause

| Cause | Benchmarks | Addressed by |
|-------|-----------:|--------------|
| Finding still true on Secure: component exported with no permission in both apps, fix is in code | 9 (ECB, NonRandomIV, ConstantKey, PBE, NoValidityCheck, UnnecesaryPerms, SQLite-execSQL, SQLlite-RawQuery, SQLlite-SQLInjection) | Nothing in P-2 applies: none of these components has a permission or `exported="false"`. Only P-8 (differential mode) drops them. |
| Finding still true on Secure: other code finding | 4 (ExposedCredentials, InsecureSSLSocket, InternalToExternalStorage, StickyBroadcast) | Not suppressible without hiding a real weakness. |
| Rule misses context that separates the apps | 5 (EmptyPendingIntent, ImplicitPendingIntent, CheckValidity, OrderedBroadcast, UniqueIDs) | P-4, P-4, P-3, ordered broadcast `getResultData` check, P-5. EmptyPendingIntent is only partly addressed: P-4 removes `pending_intent_mutable`, but a true `pending_intent_implicit` finding remains (see its row). |
| Rule misses context, but the benchmark has another false positive | 2 findings (SQL constant query in SQLite-execSQL, bound `selectionArgs` in SQLlite-RawQuery) | Worth fixing for report quality; does not change the count. |

So context-aware rules can remove at most 5 of the 18 false positives (4 once EmptyPendingIntent's implicit Intent is counted): 52 true positives with 13 false positives is precision 0.80, with 14 it is 0.79. Precision above 0.85 under the A1-1 definition is not reachable by rule context alone while the 13 remaining Secure findings are accurate statements about the Secure APKs.

No false positive comes from a taint-flow finding (P-6) or from a broadcast with a permission argument (P-7); those items are robustness changes for other apps.
