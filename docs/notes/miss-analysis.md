# Miss analysis: benchmarks with no true positive

## Source run and definitions

- Source run: `python tools/evaluate.py --no-dynamic` on 2026-11-01 (`docs/notes/evaluation-run.log`, `data/evaluation-results.csv`, section "Benchmarks with no true positive" of `docs/notes/evaluation-report.md`). That run has 16 benchmarks with no true positive. "Tool on Benign" below is what that run reports for the Benign APK.
- Current tool: the 16 Benign and Secure APKs were analyzed again on 2026-11-02 with `python src/ate.py --apk <apk> --out <scratch dir>` (static layers only), after P1-1 to P1-5 and P2-1 to P2-5. Differences from the source run are noted in the "Current tool" notes below the table. The reports in `data/eval-tmp/` were not used for this, since later dynamic and partial runs have overwritten some of them.
- True positive: the Benign APK has a finding whose CWE is in the benchmark's `cwe_ids` or `secondary_cwe_ids` in `data/ground-truth.csv`, or maps to a `cwe_ids` entry through `SECONDARY_CWE` in `tools/evaluate.py`.
- Reason categories: **wrong CWE** (the tool finds the weakness but under a CWE that does not score), **wrong component** (right CWE on a component that is not the vulnerable one), **rule not written** (no rule looks at the pattern), **ground truth gap** (the benchmark cannot score whatever the tool reports), **not statically decidable** (the Benign and Secure code cannot be told apart from the APK alone).
- Distinguishable: the proposed rule fires on the Benign APK and not on the Secure APK of the same benchmark. Judged from a diff of `Benign/app/src/main` against `Secure/app/src/main` under `benchmarks/ghera/<category>/<folder>/`.
- In-flight rules: rules that other work items are adding at the time of writing (pending_intent_mutable, dynamic_receiver_no_permission, clipboard password field, exported provider without permission, weak custom permission protectionLevel, sticky broadcast inter-app, two-APK task affinity comparison).

## Notes per benchmark

### ICC

- FragmentInjection-PrivEscalation-Lean. The current tool reports `fragment_injection` CWE-470 (medium) on `edu.ksu.cs.benign.MainActivity$1` for Benign and nothing for Secure. CWE-926 (the launcher activity reads the extra) is not reported because launcher activities are skipped by `exported-no-permission` on purpose; CWE-470 alone is enough to score.
- HighPriority-ActivityHijack-Lean. The taint analyzer maps every `startActivity` sink to CWE-926 (`SINKS` in `src/taint_analyzer.py`), whether the Intent is explicit or implicit, so Secure's explicit intent gets the same finding. The analyzer already resolves the Intent target (it tracks `setAction` and explicit classes for inter-component flows), so the fix is to use CWE-927 when the resolved target is action-only. Benign `ImageEditor` has `android:exported="false"` and an intent filter with `android:priority="5"`, so the `implicit-intent` manifest rule (which needs a missing `android:exported`) does not fire either. The weakness is in the sender: an implicit intent can resolve to Malicious's `MalImageEditor` (priority 1000).
- TaskAffinity-LauncherActivity-PhishingAttack-Lean and TaskAffinityAndReparenting-PhishingAndDoSAttack-Lean. Benign has no `taskAffinity` anywhere, so the existing `task-affinity-hijack` rule (foreign affinity or singleTask/singleInstance) has nothing to report. The attack is in Malicious (`taskAffinity="edu.ksu.cs.benign"`, plus `allowTaskReparenting="true"` in the second benchmark). Benign and Secure share the package name `edu.ksu.cs.benign`, so a two-APK comparison that only matches Malicious's affinity against the target package fires on both. It has to check the target's effective affinity: `<application android:taskAffinity="">` in Secure means no Benign activity joins the `edu.ksu.cs.benign` task. All four TaskAffinity benchmarks follow this pattern: every Secure manifest sets `android:taskAffinity=""` on `<application>`. `src/apk.py` reads the attribute with `elem.get`, so an empty string and a missing attribute are kept apart (verify that apktool keeps `taskAffinity=""` in the decoded manifest). The single-APK rule would fire on almost every real app, since the default affinity is the common case; it should be low confidence.
- UnhandledException-DOS-Lean. Benign's launcher `MainActivity` reads `getStringExtra("s1")` and `("s2")` in the click listener and calls `length()` on both with no null test and no try block; Malicious starts it without extras. Secure moves the code to `onResume`, tests `intent.getExtras() != null` and catches `NullPointerException`. CWE-248 (uncaught exception) is the same pattern seen from the handler side; one finding under CWE-476 is enough to score.
- WeakChecksOnDynamicInvocation-DataInjection-Lean. The ground-truth row has no CWE (threat model "Not drafted (tool stopped)"), so it cannot score. Benign's provider is exported with only `android:writePermission`; `call("backup", ...)` writes a file named by the caller into `getFilesDir()` with no `checkCallingPermission`. Secure adds `android:permission` (read and write) on the provider and keeps the same `call()`. The current exported-no-permission finding (CWE-926, high) on Benign's provider is correct and does not fire on Secure. This row is a data fix in `data/ground-truth.csv` and a threat model, not a rule.

### Crypto, Networking, Permission

- ExposedCredentials-InformationExposure-Lean. Benign stores a `SecretKeyEntry` with a null `ProtectionParameter` and writes the keystore to `getExternalFilesDir(null)/secretKeyStore` with `store(fos, null)`. Secure only replaces the null with `new KeyStore.PasswordProtection(char[])`. An external-storage write rule (see Storage) would fire on both apps here.
- OpenSocket-InformationLeak-Lean. Benign's `MyIntentService.onHandleIntent` opens `new ServerSocket(PORT)`, accepts and copies `openFileInput("myInfo.txt")` to the socket. Secure accepts on the same port and checks `getInetAddress().getHostName()` against `trusted.remote.com` before copying. CWE-359 (the file content leaks) would need taint from `openFileInput` to `Socket.getOutputStream().write`; Secure has the same flow inside the `if`, so only the missing peer check distinguishes them. The hostname check in Secure is itself weak (reverse lookup), which a static rule should not reward beyond "a peer check exists".
- UnpinnedCertificates-MITM-Lean. Benign's `MyTrustManager.checkServerTrusted` compares each chain certificate with the bundled `keyOne-publickey.crt`; the README says this stands in for "trust every CA-signed server". Secure trusts the bundled `keyTwo-publickey.crt` through a KeyStore and `TrustManagerFactory`. In code, both trust a single bundled certificate; the difference is which certificate, which only a run against the server shows. P1-1 tells them apart because it treats `setCertificateEntry` plus `TrustManagerFactory.init` as pinning and a custom TrustManager as not. The existing `empty_trustmanager` rule does not fire on Benign, correctly: its `checkServerTrusted` throws.
- WeakPermission-UnauthorizedAccess-Lean. `<permission android:name="edu.ksu.cs.benign.MYCP_ACCESS_PERM" />` has no `protectionLevel`, which defaults to normal. The rule must treat a missing attribute as normal (and apktool may also write `protectionLevel` as a number: 0 normal, 1 dangerous, 2 signature, 3 signatureOrSystem). The provider is currently not reported because `_protected()` in `src/surface.py` accepts any `android:permission`.

### Storage, System, Web

- ExternalStorage-DataInjection-Lean and ExternalStorage-InformationLeak-Lean. Both Benign apps differ from Secure in one call: `getExternalFilesDir(null)` against `getFilesDir()`. Neither app requests a storage permission, since the app-specific external directory needs none from API 19; other apps with `WRITE_EXTERNAL_STORAGE` can still read and write it on API 27 (before scoped storage). Whether the data is sensitive (an SSN image in one, a text the app trusts in the other) is not visible in code.
- ClipboardUse-InformationExposure-Lean. Already detected; the miss was the CWE mapping only. Benign also declares and uses a custom normal permission `santos.benign.permission` that Secure removes; it is not part of the exploit.
- WebViewAllowFileAccess-UnauthorizedFileAccess-Lean. Already detected under CWE-829; the source-run miss was the CWE only. With the merge in `surface.py` keeping one finding per (component, CWE), Benign's evidence is the `setAllowFileAccessFromFileURLs(true)` line and Secure's is `setAllowFileAccess(true)`; Secure still gets a CWE-829 finding (medium), which is why the benchmark is also a false positive.
- WebViewIgnoreSSLWarning-MITM-Lean. One-line difference in `MyWebViewClient.onReceivedSslError`: `handler.proceed()` in Benign, `handler.cancel()` plus `loadData` in Secure.
- WebViewOverrideUrl-MITM-Lean. Both overloads of `shouldOverrideUrlLoading` (`(WebView, String)` and `(WebView, WebResourceRequest)`) return `false` in Benign. Returning false is also the behavior of a WebViewClient that does not override the method, so the rule is a weak signal in general apps; it matches this benchmark because the override exists and does nothing.

## Current tool (2026-11-02)

Static re-run of the 32 APKs (all succeeded). Changes against the source run:

- FragmentInjection-PrivEscalation-Lean: Benign now has `fragment_injection` CWE-470 (medium) on `MainActivity$1`; Secure has no finding. Scores as a true positive with no false positive.
- UnpinnedCertificates-MITM-Lean: Benign now has `certificate_pinning_missing` CWE-295 (high, `(application)`); Secure has only CWE-319. Scores as a true positive; the benchmark stays a false positive through CWE-319 on Secure.
- ClipboardUse-InformationExposure-Lean and WebViewAllowFileAccess-UnauthorizedFileAccess-Lean: same findings as the source run, but P1-3 added CWE-200 and CWE-829 to their `secondary_cwe_ids`, so a `--rescore` counts both as true positives.
- The other 12 benchmarks report the same as in the source run. WeakChecksOnDynamicInvocation still cannot score until its ground-truth row has CWEs.

Checked in the decoded APKs (apktool output): Secure's decoded manifest of TaskAffinity-LauncherActivity-PhishingAttack-Lean keeps `android:taskAffinity=""` on `<application>`; WeakPermission's Benign decoded manifest has `<permission android:name="edu.ksu.cs.benign.MYCP_ACCESS_PERM"/>` with no `protectionLevel`; the smali patterns quoted in the implementation notes below were read from the decoded Benign APKs. TaskAffinity-PhishingAttack-Lean's Benign also sets `taskAffinity=""` on `<application>` (its weakness is the foreign activity affinity that `task-affinity-hijack` already reports), so the proposed default-affinity rule does not fire there.

## Implementation notes for the rules not written

- `default_task_affinity` (CWE-1021, manifest, `(application)`, low). Fire when `application['taskAffinity'] is None` (attribute missing; an empty string means no affinity) and the app has a launcher activity, and no activity sets its own `taskAffinity`. Benign: attribute missing. Secure: `taskAffinity=""`.
- `null_deref_intent_extra` (CWE-476, smali, the class holding the method). In one method: `invoke-virtual {vI, vK}, Landroid/content/Intent;->getStringExtra(Ljava/lang/String;)Ljava/lang/String;` then `move-result-object vX`; later an `invoke-*` with `vX` as receiver (for example `Ljava/lang/String;->length()I`) with no `if-eqz vX`/`if-nez vX` in between, not inside a `:try_start`/`:try_end` range whose `.catch` is `Ljava/lang/NullPointerException;`, `Ljava/lang/RuntimeException;`, `Ljava/lang/Exception;` or `Ljava/lang/Throwable;` (or `.catchall`), and no reassignment of `vX`. Restrict to classes of exported components and their inner classes. Benign `MainActivity$1.onClick`: lines 68 to 96 of the smali, no branch, no try. Secure: calls inside a try with `catch NullPointerException` and after an `if-eqz` on `getExtras()`.
- `keystore_entry_unprotected` (CWE-922, smali, the class). `invoke-virtual {vS, vA, vE, vP}, Ljava/security/KeyStore;->setEntry(Ljava/lang/String;Ljava/security/KeyStore$Entry;Ljava/security/KeyStore$ProtectionParameter;)V` where the register model has `vP` = `const/4 vP, 0x0`. Benign: `vP` is `v1`, set by `const/4 v1, 0x0` and not reassigned before the call. Secure: `vP` comes from `new-instance Ljava/security/KeyStore$PasswordProtection;`.
- `server_socket_no_peer_check` (CWE-940, smali, the class). Method has `invoke-direct {vS, vP}, Ljava/net/ServerSocket;-><init>(I)V` (or `(II)V`; the three-argument form with an `InetAddress` bound to loopback is safer) and `Ljava/net/ServerSocket;->accept()Ljava/net/Socket;`, the result is used with `Ljava/net/Socket;->getOutputStream()` or `getInputStream()`, and the method calls none of `Ljava/net/Socket;->getInetAddress`, `getRemoteSocketAddress`, `getPort`. Benign `MyIntentService.onHandleIntent`: init, accept, `getOutputStream`, no peer call. Secure: `getInetAddress()` then `getHostName()` and `equals`.
- `weak_custom_permission` (CWE-926, manifest, the protected component). For each exported component, take `permission`, `readPermission`, `writePermission`; if any names a `<permission>` declared in the same manifest whose `protectionLevel` is missing, `normal`, `dangerous`, `0x0` or `0x1`, report it. Benign: no `protectionLevel`. Secure: `signature`. This is the in-flight rule.
- `external_storage_io` (CWE-922, smali, the class). A register set by `move-result-object` after `getExternalFilesDir`, `getExternalCacheDir`, `getExternalFilesDirs`, `Landroid/os/Environment;->getExternalStorageDirectory` or `getExternalStoragePublicDirectory` reaches `Ljava/io/File;-><init>(Ljava/io/File;Ljava/lang/String;)V` (or `getAbsolutePath` then `File.<init>(String)`), and the File reaches `FileInputStream`/`FileReader` (data injection) or `FileOutputStream`/`FileWriter` (information leak). Benign: `getExternalFilesDir(null)`. Secure: `getFilesDir()`. Also fires on both ExposedCredentials APKs.
- `webview_ssl_proceed` (CWE-295, smali, the WebViewClient subclass). Method `onReceivedSslError(Landroid/webkit/WebView;Landroid/webkit/SslErrorHandler;Landroid/net/http/SslError;)V` containing `invoke-virtual {p2}, Landroid/webkit/SslErrorHandler;->proceed()V`; high when there is no `if-` before it. Benign: `proceed()` after a `Log.d`. Secure: `cancel()`.
- `webview_override_allows_all` (CWE-829, smali, the WebViewClient subclass). Method `shouldOverrideUrlLoading(Landroid/webkit/WebView;Ljava/lang/String;)Z` or `(Landroid/webkit/WebView;Landroid/webkit/WebResourceRequest;)Z` with no `if-` instruction and whose only return is `return vN` after `const/4 vN, 0x0`. Benign: both overloads return false. Secure: both call `getOverrideUrlSettings`, which compares the URL and returns true for untrusted ones.
- `implicit_intent_activity` (HighPriority, CWE-927; a change to the taint analyzer, not a new rule). In `src/taint_analyzer.py`, when the Intent reaching a `startActivity` sink has an action but no explicit class or package, report CWE-927 instead of CWE-926. Benign: `new Intent()` + `setAction("edu.ksu.cs.benign.imageEditor")` + `putExtra`. Secure: `new Intent(Context, Class)`.

## Research gap

Of the 16 misses, none is a pure static-analysis limit in the sense that the Benign and Secure APKs are identical in what a static rule can read: every pair differs in at least one manifest attribute or call. The counts by reason (source run): rule not written 12 (FragmentInjection and UnpinnedCertificates since covered by P1-2 and P1-1; WeakPermission targeted by an in-flight rule), wrong CWE 3 (HighPriority, ClipboardUse, WebViewAllowFileAccess; the last two now score through `secondary_cwe_ids`), ground truth gap 1 (WeakChecksOnDynamicInvocation). Wrong component: none.

The limits that remain are about meaning, not syntax:

- Intent and trust are not in the code. UnpinnedCertificates differs only in which bundled certificate each app trusts; the Benign code looks like pinning and the README defines it as CA trust. The P1-1 rule separates the pair through how the certificate is loaded (custom TrustManager against TrustManagerFactory), not through what is trusted, so it would also flag a correct custom pinning TrustManager.
- Data sensitivity. ExternalStorage-InformationLeak (an SSN image), ClipboardUse (an SSN field) and OpenSocket (`myInfo.txt`) leak sensitive data; a static rule sees a file, a clipboard copy or a socket write, and can only guess sensitivity from names. CWE-359 in particular needs that judgement.
- Two-app weaknesses. The TaskAffinity misses and HighPriority are only exploitable when another app declares a matching affinity or intent filter. A single-APK rule can only flag the precondition (default task affinity, implicit intent to an own action), which nearly every real app has. These rules separate Ghera's Benign and Secure apps but would have low precision outside the benchmark; the two-APK comparison is the more exact check.
- Runtime values. UnhandledException needs the absence of a null check on an extra the attacker controls; a branch-free register model handles the Benign case but not checks made in a called method or through `hasExtra`. OpenSocket's Secure fix is a hostname comparison that is itself weak (reverse DNS); a static rule can see that a peer check exists, not that it is sound.
- Default behavior. WebViewOverrideUrl's Benign override returns false, which is the same as not overriding at all. The rule matches the benchmark's code shape, not a property that separates safe from unsafe WebViews in general.

In short, every miss can be closed for the Ghera pairs with a manifest or smali rule, but for about half of them (TaskAffinity x2, HighPriority, UnpinnedCertificates, WebViewOverrideUrl, the CWE-359 part of the information leak benchmarks) the rule detects a precondition or a code shape that is also common in safe apps, and needs a second app, a run, or knowledge of data sensitivity to be precise.
